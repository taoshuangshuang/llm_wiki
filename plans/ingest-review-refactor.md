- 状态：本地实现已完成；实现取舍、验证结果与模型效果边界见 [实施与验收记录](ingest-review-implementation.md)。
- 基线：当前工作区已有的入库、语义复用、验收及并发提交实现；保留用户现有未提交改动。

> 后续设计（2026-10-29，待实施）：[长文子块串行入库与分批审阅设计](长文子块串行入库与分批审阅设计.md)。后续以来源子块独立入库、独立审阅，全链路串行；每个审阅任务按 10 页分批，每批检索预算 60 秒。本文件保留此前方案及实现背景，不表示后续设计已经落地。

## 1. 目标与已确认决策

本次改造将文件写入与自动审阅分开：先完成可完成的写入，再独立检查问题。内容分歧、主题不确定和合并质量问题不导致整个来源反复重新入库。

已确认的决策如下：

1. 独立 review 放到文件合并、规范化和实际写入之后。
2. 审阅作为独立后台任务，持久化排队，失败后可以仅重跑审阅。
3. “本轮页面”指单个来源文件的一次逻辑入库，不指一次文件夹批量导入。
4. 生成截断时保存已完成页面，标记部分写入，保留未完成输出；后续仅补写未完成部分。
5. 合并目标明确但存在内容歧义或合并质量问题时，以本次导入生成内容为准覆盖；保存旧快照并提出审阅事项。
6. 无法确定唯一合并目标时，使用独立的新路径写入，不随意覆盖某一候选旧页。
7. review 面向整个知识库检索，再读取相关正文；不是每次把全库全文装入上下文。
8. 覆盖前后冲突需要旧页快照；本轮页面也要相互检查。
9. 缺页既检查知识是否缺失，也检查已有内容是否值得整理为独立页面。
10. 内容遗漏与内容失真统一展示为“内容校验”，合并问题不再细分界面类型。
11. 移除左下角任务面板，主导航在“资料”之后新增“导入过程”页签，保留完成历史。
12. 展示优先级固定为：合并问题、内容冲突、内容校验、格式校验、缺页建议、疑似重复、研究建议；子类沿用主类优先级。
13. review 与 acceptance 合并为统一的后台 review；共用一个任务入口、状态、结果协议和持久化流程，格式与内容校验作为内部检查步骤。
14. 统一召回入口支持检索通道开关，至少包含向量、关键词和索引页；入库、审阅及问答遵守相同的有效配置，降级不能启用用户明确关闭的通道。
15. 统一检索返回可定位、可核实版本的正文证据和页面引用关系；共用召回、融合、证据展开与预算逻辑，各阶段保留自身的业务判断。
16. 对每个问题／检索目标，向量、关键词和索引页通道分别取 top 5，RRF 融合后最终最多返回 top 5；多个问题分别计算，受任务总预算约束。

技术目标是让写入结果、版本证据、后台任务和待审阅事项可追溯、可恢复、可单独重试。模型调用成功、写入完成、自动审阅完成和人工处理完成是不同状态。

## 3. 整体流程与职责

    来源读取与固定版本
        → 来源分析、页面生成
        → 候选召回、目标选择
        → 保存写入意图和旧页证据
        → 正常合并，或采用明确的写入降级方式
        → 规范化、实际写入、记录最终版本
        → 更新可更新的索引，形成入库结果与审阅请求
        → 释放写入任务名额
        → 独立后台审阅
            → 格式校验、内容校验
            → 本轮页面冲突、覆盖前后冲突
            → 全库相关证据检索
            → 已有知识冲突、重复、缺页和研究建议
            → 合并证据相同的事项、持久化结果、更新界面

模块建议分为四组，不为每种审查单独创建公共入口：

- 写入记录模块：保存来源版本、页面快照、写入结果、处理事件及恢复信息。
- 审阅执行模块：接收一次入库记录，组织校验、检索、模型判断并返回统一结果。
- 后台审阅队列模块：负责排队、取消、恢复、版本失效、结果提交及仅审阅重试。
- 导入过程视图：展示持久化运行记录和任务进度，不负责启动或维持后台执行。

检索由统一 Module 提供一个证据检索入口，内部组织向量、关键词、索引页及图关系 Adapter，隐藏候选映射、融合、正文核实和降级细节。文件读取、检索、模型调用和时钟以可替换依赖提供，测试通过实际入口验证输入输出契约。

review 与 acceptance 统一为一个后台 review Module：一次调度覆盖所有适用检查，一份报告记录各步骤状态，一处提交待审阅事项。内部复用原 acceptance 的来源分段、结构检查及覆盖核对能力，不再保留两套各自排队、写报告和发布事项的生产流程。旧 acceptance 文件名和字段仅在迁移兼容中保留。

生成阶段不再正式发布缺页、重复和冲突结论，避免合并前判断进入最终待办。兼容旧生成模板时，旧 REVIEW 块只能作为线索，经过写入后核实再发布。

## 4. 一次入库的身份与业务记录

### 4.1 本轮与补写

- runId 标识一个来源固定版本的一次逻辑入库。
- attemptId 标识本轮首次执行或补写尝试。
- 相同来源版本的补写仍属于原 runId，本轮页面包含此前成功写入与此次补写的最终页面。
- 来源实质变化后创建新的 runId，不沿用旧版本的未完成任务。
- 覆盖前快照指本轮首次修改某个路径前的内容；本轮多次合并不能将中间产物误认为入库前旧知识。
- 同一知识页由多个来源更新时，各次记录独立，使用页面版本判断结果是否仍适用。

### 4.2 建议持久化布局

在项目内部状态目录新增以下记录，具体文件拆分可在实施时根据原子写能力调整：

实际实现采用 `.llm-wiki/ingest-runs/<runId>/source.json` 与 `manifest.json`。manifest 合并保存任务状态、提交意图、页面快照、工作单元映射、检查步骤及历史报告；持久的 `reviewRequested` 即后台待办，避免另外一份队列索引与业务记录不同步。

    .llm-wiki/ingest-runs/<runId>/manifest.json
    .llm-wiki/ingest-runs/<runId>/source.json
    .llm-wiki/ingest-runs/<runId>/pages/<受控页面键>.json
    .llm-wiki/ingest-runs/<runId>/events.json
    .llm-wiki/ingest-runs/<runId>/review.json
    .llm-wiki/review-queue.json

内部快照文件名使用应用产生的受控键，真实 Wiki 路径作为记录字段，不能直接采用模型输出作为内部文件系统路径。

| 记录 | 必要内容 |
|---|---|
| 来源 | projectId、相对路径、来源身份、内容指纹、本轮实际提取文本与时间 |
| 页面 | 请求路径、最终路径、修改前／写入后正文及指纹、写入方式、来源关联 |
| 处理事件 | 原因、实际采取的方案、成功与否、可验证的风险、关联页面与证据 |
| 运行状态 | 写入状态、补写检查点、审阅请求、审阅状态、取消／失败原因 |
| 审阅结果 | 各检查完成情况、检索范围、问题及证据、实际使用的模型与规则版本 |

业务记录只保存模型配置身份及实际使用信息，不保存 API 密钥等凭据。执行时通过现有配置体系取得凭据。旧快照不因待办被忽略而立刻删除；首期以用户显式清理历史为准，不引入自动清理策略。

### 4.3 写入与后台交接的恢复约定

1. 在覆盖前可靠保存旧正文及写入意图，再提交实际页面。
2. 页面成功写入后记录写后指纹和结果；崩溃恢复时能够核实某次写入是否完成。
3. 入库结果中持久化“需要后台审阅”的请求，再释放写入任务。
4. 审阅队列是运行记录的调度索引；重启时可从尚未完成的请求恢复，不能只依赖内存回调。
5. 写入与结果登记之间发生崩溃时，按意图、快照和当前页面指纹恢复；无法核实时标记需恢复，不按旧意图盲目覆盖当前文件。
6. 业务记录、页面或审阅请求持久化失败属于实际存储问题。保留已写页面，并明确显示交接未完成；恢复时优先补登记，不重新生成全部页面。

继续沿用项目短提交锁和提交前版本校验。模型等待不占项目锁；目录、路径和底层写入授权仍由现有约束保护，不能把未获准或实际未发生的写入记为成功。

候选检索与目标判断在准备正文时完成，提交前不因新增页面再次检索或核对主题；新增页面的疑似重复统一交给后台审阅。提交前仍核对已消费文件的快照，包括新建目标此前不存在的约定，防止覆盖并发修改或被其他写入者占用的目标路径。首次无法确定唯一目标时独立保存生成稿，并固定候选全文供后台审阅。

## 5. 写入降级与错误分类

| 情况 | 写入策略 | 记录与后续处理 |
|---|---|---|
| 唯一目标明确、合并正常 | 正常合并并写入 | 保存前后快照 |
| 无法确定唯一主题或有多个合理目标 | 分配安全、唯一的新路径，保留原候选 | 合并问题：说明另存位置、候选及重复／分散风险 |
| 模型已返回，但主题判断协议不完整或结果无法解释 | 不据不完整判断选择旧页，采用独立路径 | 合并问题，供后续确认目标 |
| 目标明确，内容取舍不确定 | 本次生成内容优先，必要时以该稿覆盖目标 | 合并问题；review 检查覆盖前后冲突及内容变化 |
| 合并输出截断、正文异常缩减、结果结构不合格 | 拒绝该份合并结果，采用已有完整新生成稿写入 | 合并问题：明确未采用合并结果及回退方式 |
| 完整 FILE 块存在格式或 schema 质量问题 | 能明确规范化的先规范化；其余在合法 Wiki 路径保存并报告 | 格式校验；不为绕过问题自动修改项目 schema |
| 模块分类等辅助模型返回无效判断 | 不因分类质量阻止保存正文 | 记录降级结果，相关字段问题进入格式校验 |
| 网络、鉴权、额度、外部模型服务不可用 | 按现有环境故障机制暂停或失败，保留已写部分 | 不伪造检查或合并成功；恢复只处理未完成阶段 |
| 旧页无法读取、快照无法保存、磁盘或权限故障 | 不继续不可追溯的覆盖，保留已完成页面 | 显示实际写入限制及恢复入口 |
| 页面或来源在模型等待期间变化 | 重读并重新核对，保留用户／其他任务的新版本 | 这是并发版本变化，不按内容歧义强制覆盖 |
| 用户取消 | 停止新的提交，保留已完成的原子写入 | 可取消导入与取消审阅分别记录 |

内容歧义需要合并返回明确的判断信息；不能把一篇格式正常的返回文本直接解释为“没有歧义”。合并处理结果应为结构化结果，至少区分正常合并、采用新稿、独立建页及相应原因。

既有的注释、来源追溯和非冲突正确内容仍应由正常合并保留。覆盖是明确的降级决策，review 中必须能说明旧页中哪些内容未进入新页；不能因为采用新稿，就将全部旧来源都标成新稿当前事实的依据。

## 6. 部分写入与仅补写

生成截断时只提交完整、路径安全且可定位的页面块，不把半截 FILE 块强行当作完整页面。剩余原始输出保存为内部现场，不充当可检索的正式知识页。

写入状态区分：等待、进行中、完整写入、部分写入、失败、已取消。部分写入不是完整成功，也不是全部失败。

- 持久化已完成路径、版本、分析计划、未完成输出和继续生成所需信息。
- 未完成部分可能包括尚未生成的页面，不能假定所有缺失路径都能从截断文本中提前解析出来。
- “继续补写”只继续尚未完成的内容，不默认重新生成、覆盖已完成页面。
- 补写前核对来源版本和已写页面版本，遇到后续人工修改按最新版本重新处理。
- 完成判定需要模型续传结果与实际写入结果一致，不能只相信模型自报完成。
- 完整来源成功缓存只在所有应写内容完成后登记；部分写入使用检查点，不能命中完整成功缓存。
- 部分写入也触发后台审阅：可检查已写页面及处理事件；全来源覆盖检查明确记录“来源入库未完成”，避免将尚待补写的内容全部报成遗漏。
- 补写完成后刷新本轮最终快照，并重新安排受影响检查。旧审阅结论保留版本信息，不直接叠加成重复事项。

如果完全没有可写知识页，显示未生成有效页面及可恢复原因，不把只保存模型输出或日志记为成功入库。

## 7. 独立后台审阅

### 7.1 生命周期

建议任务状态为：等待、执行中、已完成、部分完成、未完成、已取消、已被新版本替代。是否存在待处理事项另外统计。

- 写入任务交接成功后即可释放执行名额，不等待审阅模型。
- 审阅在应用级执行，不依赖“导入过程”或“审阅”页面是否挂载。
- 首期默认单项目一次执行一个审阅任务，独立于写入并发名额；限制可在后续按实际耗时调整。
- 切换页签不影响任务；首期沿用当前项目调度模式，切换项目暂停／取消旧项目请求并保留可恢复状态，返回后续跑。
- 关闭应用后不继续运行，重启后恢复；不能把后台任务理解成独立于应用的常驻服务。
- 环境性临时失败可有限重试；协议错误允许一次针对性重试，仍失败则保留“未完成”，不无上限循环。
- “重试审阅”只重跑未完成或失效检查，不重新生成和写入页面。
- 审阅失败不会把已完成写入改为失败，也不会触发入库队列重新覆盖文件。

上述并发及有限重试次数是实现建议，不新增一组必填用户配置；实施时集中定义常量并测试，不散落在调用方。

### 7.2 检查组织

统一 review 的输入是一次入库记录及执行依赖，输出是统一审阅报告与事项；入库调用方不再分别调用 acceptance 和独立 review。格式、内容、冲突等步骤使用同一结果协议和证据结构，由同一任务维护完成、失败及重试状态。

合并流程不要求七类问题都塞进一次模型调用。一次后台任务可以包含程序检查和多次有明确材料范围的请求：

1. 从写入事件直接生成可证实的合并问题。
2. 程序检查 YAML、字段类型、页面路由及可以确定的引用问题。
3. 来源对照最终页面，执行内容遗漏与失真检查。
4. 以具体主张为单位检查本轮页面互相冲突与覆盖前后冲突。
5. 检索全库相关证据，检查与已有知识冲突、重复、缺页和研究建议。
6. 核实证据、归类、去重，提交统一事项与完成状态。

每个检查保存独立完成情况和可恢复检查点。前一项失败不要求丢弃其他已经得到的有效结果；重试只处理失败或证据失效步骤，部分完成不能显示为“未发现问题”。最终结果由统一入口核实、去重和提交，内部检查步骤不直接写入全局事项 Store。

### 7.3 版本一致性

本轮页面使用写入时固定的最终快照。候选旧知识使用实际读取到的当前正文，并保存消费时的版本指纹。

提交审阅结果前短锁核对涉及页面版本。页面已经变化时，旧结论标记为历史／待复核，不直接作为当前已核实问题发布；重新安排受影响检查，并限制连续重排次数，避免活跃页面不断更新导致无限审阅。

同一来源已经产生更新的 runId 时，未开始的旧审阅可以被替代。仍需保留旧记录、覆盖快照和人工处理历史，不能把旧任务结果写回新任务状态。

## 8. 统一证据检索算法与上下文预算

### 8.1 召回步骤

- 从本次来源、实际变化的主张、页面主题及明确引用提取查询，分析结果仅作为辅助线索。
- 根据有效通道配置执行召回：启用且可用的向量通道召回相关片段；启用的关键词通道补充名称、文件名、术语及正文精确查询。相似度只影响召回排序，不直接决定重复或冲突。
- 无向量能力时，若索引页通道已启用，先查索引选择相关知识点再读页面；索引未命中或不完整时，只能使用已启用的关键词等通道补充，不能忽略关闭设置。
- 使用项目真实文件清单解析页面身份，处理别名、标题与实际文件名差异。
- 命中片段用于定位，结论需要读取当前相关正文与必要的上下文；不能把过期向量片段当作最新证据。
- 本轮所有最终页面作为已提供材料直接纳入检查，不等待向量更新完成；其他已提交但尚未建立向量索引的页面，通过已启用的索引、词法或图通道发现。
- 多个命中片段可以来自同一页面；不能只因页面相同就丢掉有独立证据价值的片段。
- 本轮页面集合同时参与互查；与全库集合去重后，避免将同一页面对同时报告为本轮冲突和已有知识冲突。

检索返回必须区分正常有命中、正常无命中、向量不可用、检索失败、证据不完整等情况。无命中不能证明知识不存在。缺页建议保存查询与已核对范围，只有证据足够时发布明确建议；否则记录该项检查未完成或需要扩大查询。

### 8.2 预算

system 放规则，user JSON 放本次材料。按当前审阅模型配置核算完整请求、JSON 序列化开销、输出预留和必要余量。

现有 maxContextSize 按字符计量，max_tokens 按 token 计量，需要明确换算估计；不能直接相减，也不能承诺字符估算等于模型精确 token 计数。

- 来源覆盖检查不静默截去尾部；分段后逐段检查，段外内容不判为遗漏。
- 候选正文过长时按相关章节展开，保存已检查的范围；证据被截断时不得输出确定性结论。
- 本轮多页互查先按主张召回候选关系，避免对所有完整页面做无条件平方级模型调用。
- 每轮扩展查询、候选量和请求次数设置有限上限，记录达到上限的检查状态。
- 全量索引和整份分析不重复传入每次请求，只有任务需要的项目目的、schema 规则和证据才进入材料。

### 8.3 召回通道开关

统一入口区分“用户允许使用”“当前能力可用”“场景本次需要”，最终只执行三者交集。场景不能自行打开用户关闭的通道，向量失败也不能自动绕过关闭设置改用关键词或索引页。

| 开关 | 控制范围 | 说明 |
|---|---|---|
| 启用向量检索 | 根据语义相似性召回片段 | 与 Embedding 模型、服务及索引可用性分别记录；打开开关不代表当前服务可用 |
| 启用关键词检索 | 按正文词项、短语、标识符及文件名／标题／别名做词法匹配 | 关闭索引页通道不等于禁止此通道匹配页面自身标题 |
| 启用索引页检索 | 利用 wiki/index.md 中的目录、名称和说明选择页面，再读取实际正文 | 索引是导航线索，不直接将索引说明当成正文事实；不限定其他通道只能查索引已收录页面 |
| 启用图关系扩展 | 从有效种子页面补充链接、反向链接等相关页面 | 建议作为高级开关；没有可靠种子时不进行无目标扩展，邻接关系不等于正文相关 |

配置层级建议采用全局默认与项目覆盖，统一设置页显示当前有效值及来源。入库、审阅和问答通过同一解析逻辑取得配置，场景策略可以缩小通道集合及预算，不建立互不相干的默认开关。默认组合需结合后续算法讨论确定，不能把默认推荐当成已确认选择。

本轮页面、来源原文、覆盖前快照及用户明确附加的页面属于任务已提供材料，不属于全库召回通道。它们仍可直接读取；页面版本核实也不是可关闭的召回通道。尚未索引的其他页面如何被发现，仍须遵守已启用的召回方式，不能借“补查新页”暗中执行已关闭的关键词检索。

全部通道关闭时允许保存配置，但必须明确显示“全库检索未启用”。入库写入继续；review 执行不依赖全库召回的检查，并将依赖全库的部分标记为未执行，不能据此生成确定性缺页、重复或已有知识冲突结论。问答可使用明确提供的材料，不声称已经检索整个知识库。

每次执行记录启用通道、实际运行通道、禁用／不可用／失败原因和降级方式。配置在任务启动时固定为本次执行版本，修改配置影响后续任务；重试时明确记录采用的新配置，避免无法重现检索结果。

如果后续引入专用 rerank 模型，重排单独配置；它只处理已召回材料，不获得额外启用召回通道的权限。

### 8.4 统一入口与输入输出

建议公共入口为 `retrieveEvidence(request) -> RetrievalResult`。统一的是找证据的能力，不将合并目标判断、审阅结论或问答生成塞进检索入口。调用方提供任务目标、检索范围及预算，无需自行拼接多个通道、换算各自分数或解析旧向量身份。

以下 TypeScript 形状用于说明跨前后端契约；具体类型名与传输方式在实施时确定，不新增第二套独立的检索实现。

```typescript
type RetrievalChannel = "vector" | "keyword" | "indexPage" | "graph";

interface RetrievalRequest {
  projectId: string;
  scene: "ingest" | "review" | "qa" | "search";
  targets: Array<{ id: string; text: string }>;
  scope: {
    corpus: "wiki" | "sources";
    includePaths?: string[];
    excludePaths?: string[];
  };
  // 只能缩小项目有效配置；true 不能打开项目已禁用的通道。
  channels?: Partial<Record<RetrievalChannel, boolean>>;
  // 引用已提供的材料，由内部受控读取；不反复传入整份快照。
  context?: { runId?: string; providedPaths?: string[] };
  budget: {
    // 单个目标、单轮检索：各通道默认 5，RRF 最终默认 5。
    channelTopK: { vector: number; keyword: number; indexPage: number };
    resultLimit: number;
    contextCharLimit: number;
    candidateLimit: number;
    queryLimit: number;
    timeLimitMs: number;
  };
}

interface RetrievalResult {
  status: "completed" | "partial" | "disabled" | "failed";
  evidence: Array<{
    id: string;
    targetIds: string[];
    path: string;
    title: string;
    revision: string;
    headingPath: string[];
    range: { startLine: number; endLine: number };
    text: string;
    rank: number;
    retrievalSources: Array<{
      channel: RetrievalChannel;
      queryId: string;
      rank: number;
    }>;
    relationIds: string[];
  }>;
  relations: Array<{
    id: string;
    fromPath: string;
    fromRevision: string;
    toPath?: string;
    targetText: string;
    kind: "wikilink" | "related" | "markdownLink";
    anchor?: string;
    range?: { startLine: number; endLine: number };
    nearbyText?: string;
    resolution: "resolved" | "missing" | "ambiguous";
    usedForRecall: boolean;
  }>;
  targetResults: Array<{
    targetId: string;
    status: "matched" | "no_match" | "incomplete" | "not_run";
    evidenceIds: string[];
    reason?: string;
  }>;
  execution: {
    configVersion: string;
    queries: Array<{ id: string; targetId: string; text: string }>;
    channelStates: Array<{
      channel: RetrievalChannel;
      status: "completed" | "disabled" | "unavailable" | "failed" | "skipped";
      reason?: string;
    }>;
    warnings: string[];
    budgetReached: string[];
    elapsedMs: number;
  };
}
```

字段约定：

- `targets` 支持一次任务的多个问题或主张，每项保留自身证据与执行状态；不能只按总排序取前几条，导致某个主题完全没有检索机会。
- 项目身份、范围及来源权限由受信任调用方确定，模型不能自行扩大。`sources` 范围不自动转查 Wiki；路径列表须在当前项目与指定语料内解析，来源语料不适用的索引／图通道标记跳过。
- 路径采用项目相对路径，身份解析结合真实清单与内部页面标识。`revision` 是本次实际读取正文的内容指纹；行号从 1 起始，对应该版本正文，范围包含两端。未能定位的候选不伪造行号，应补读或记录证据未完成。
- `retrievalSources` 解释候选从哪些通道和查询获得；`relations` 记录真实引用边及必要上下文。反向链接通过边的方向表达，不复制为相反方向的新事实边。无法取得锚点、附近文本或范围时省略，不推测补全。
- `completed` 只表示本次限定范围和预算内的计划检索完成，不表示穷尽全库。`no_match` 与通道未执行、异常、超时严格区分；存在有效证据但部分执行失败时返回 `partial` 并保留证据。
- 完全关闭或没有适用的召回通道时，全库召回状态为 `disabled`，原因区分用户禁用与场景不适用；已提供材料仍可供当前任务使用。计划通道全部不可用或失败、且没有有效证据时为 `failed`，不能返回正常无命中。
- 证据相关性分数、RRF 分数都不是事实正确概率。公共结果不提供“确定冲突”“确定重复”“确定缺页”布尔结论。

### 8.5 算法执行流程

    解析项目、范围、有效配置与总预算
        → 按目标生成有限查询计划
        → 启用通道召回候选
        → 规范页面身份、合并重复命中、融合排名
        → 从有效种子执行有限图关系扩展
        → 读取当前正文、校正过期片段及引用定位
        → 相关性重排、按需展开正文、分配多目标预算
        → 返回正文证据、引用关系、各目标状态与执行记录

1. **固定配置与范围。** 取得全局默认、项目覆盖和场景约束的交集，固定本次配置版本。配置、超时、候选量及正文预算在内部统一核算；任何降级不得扩大语料范围或打开禁用通道。
2. **制定查询。** 保留原始问题或主张，同时抽取术语、别名、主题和明确引用。保留否定、数字、版本、环境条件及原始技术标识符；不能只剩抽象摘要。长材料按主题拆为多个目标。首期不要求每次先调用模型改写；若启用模型拆解或补充查询，其次数也计入任务预算。
3. **分别召回。** 向量召回语义相关片段；关键词召回词项、短语、标识符及标题／文件名／别名；索引页提供导航候选再读取对应实际页面。独立通道可并行。无向量时优先使用已启用的索引页路径，再用已启用的词法通道补查。关键词关闭时，索引通道不能暗中进行全库正文词法搜索。
4. **识别与合并候选。** 向量 chunk、索引条目和图节点统一解析到真实页面。同页面、同版本的相同或重叠证据合并，保留召回来源；不同章节或同章节有独立内容的片段仍保留。旧版以文件名映射的歧义不能任意选择目标。本轮快照与其他版本不能只因路径相同而合并。
5. **融合排序。** 对同一目标，各通道先按自身规则排序并分别取 top 5，再用 RRF 融合，不直接相加向量距离、词频分和索引排序。首期可沿用现有 `k = 60`，候选 `d` 的融合分为 `Σ 1 / (k + rank_c(d))`；名次从 1 开始，未命中通道不贡献。`k` 是平滑参数，与最终 top 5 无关。多个查询改写先在各通道内部合并、截取 top 5，同一内容不会因反复改写而得到无限投票。页面级候选先融合，保留其下独立片段供最终证据选择。
6. **有限关系扩展。** 仅在 graph 通道启用且有有效种子时，沿真实引用边补充候选。首期建议一跳，限制种子数、每页边数和总候选数；二跳作为后续可选策略，不能递归遍历全库。图候选经正文相关性核实后形成有序列表并入同一 RRF 融合，不占固定最终结果配额，也不突破最终 top 5。
7. **核实当前版本。** 命中旧向量时读取当前正文，通过实际内容重新定位；无法定位则丢弃旧证据并记录，必要时在允许通道内补查。不能将旧片段换上新版本指纹后直接返回。已明确提供的本轮页面与快照独立参与任务；其他未索引页面只能通过已允许通道发现。
8. **核实相关性并展开。** 核实正文、标题、章节与术语条件的相关性，排除无效候选，避免单靠词频或链接数提升结果。相反观点也可能是最有价值的相关证据，不能按“同意本次观点”筛选。首期最终排序使用 RRF，不默认增加后置模型重排；无效候选按融合顺序补位。专用重排模型如后续启用，须单独确认排序策略且仍遵守 top 5。按命中片段、邻近段落、完整章节、必要时全文逐级展开，尽量保留完整表格、代码和适用条件。
9. **按目标装配返回。** 每个目标按 RRF 顺序选择证据，最终最多返回 5 条正文证据；图候选与正文展开不增加最终条数。在总预算下给不同目标分配机会，去掉无新增信息的重复文本，保留独立证据；不足的目标明确标记。每次调用只执行一轮有界计划，返回实际查询、通道状态、正文范围和预算耗尽原因。

如果调用方发现某项判断缺少证据，可针对具体缺口发起下一次检索，但须共享上层任务的累计候选、请求次数、耗时和上下文预算。检索内部不再嵌套无限模型循环，防止问答或 review 的多轮执行与内部重试相乘。

### 8.6 引用关系进入模型材料

当前问答已经提供有限的 `outgoingLinks`、`backlinks`、`relatedTo`、`linkCount`，但尚未统一进入入库独立 review。改造后所有调用方使用同一证据协议，不能只在搜索界面或事件日志展示关系，而在模型材料中丢失。

- 识别正文 `[[页面]]`、带显示别名或章节锚点的 Wiki 链接、frontmatter `related`，以及可解析到项目内 Markdown 页的普通链接。排除代码块中的示例链接和图片引用；外链不触发自动联网。
- 保留有向边、引用来源版本、目标身份、锚点和引用附近的文字。标题重名、文件名差异与别名解析不唯一时明确标记歧义。目标缺失的边可进入格式或缺页检查，但仅凭悬空引用不自动认定需要新建知识页。
- 图召回使用双向邻居时，仍须保留原始引用方向。`A → B` 只能说明 A 引用了 B，不能当成 B 支持 A，亦不能当成模型已经读过 B。
- 对每段正文证据返回其 `relationIds` 和相关边；若来自图扩展，说明种子页与路径。模型可据此请求读取具体目标正文，禁止根据页面名称或链接存在性直接裁定冲突、重复和知识覆盖。
- 索引页与高连接导航页不能仅凭大量边成为强证据；图扩展不能借助索引枢纽绕过已关闭的索引页通道。明显无关的邻居不占最终名额。
- 传给模型的 user JSON 同时包含必要的正文、证据标识、版本、位置、关系及执行缺口；system 保留使用规则。关系摘要、正文和 JSON 包装共同计入上下文预算，超限时保留本次判断相关的边，明确说明省略范围，不输出无界全库图。

### 8.7 各阶段复用与迁移

| 使用阶段 | 检索输入重点 | 检索之后由调用方处理 |
|---|---|---|
| 入库目标选择与合并 | 来源主题、生成稿、明确引用 | 读取候选必要全文，判断复用目标与合并方式；不以相似度直接认定重复 |
| 后台 review | 本轮实际修改的主张、主题、待核实概念 | 结合来源及前后快照判断冲突、重复、缺页与研究建议，保存双方证据 |
| 问答 | 用户问题、明确限定的语料及相关对话条件 | 综合证据回答并引用；缺证据时按总预算补查或说明不足 |
| 搜索 | 原始查询与用户范围 | 展示命中、片段及召回原因，不额外调用模型裁定事实 |

来源内容校验仍采用来源逐段对照，不能被统一检索返回的 top-K 替代，否则未召回内容会被错误地视为已经校验。覆盖前后冲突必须使用固定旧快照，不能通过全库检索重新取当前页冒充旧版本。

实施建议以现有 Rust 搜索核心作为统一执行位置，通过 Tauri／现有后端调用方式接入前端入库及 review，Agent 和 HTTP／MCP 使用同一核心。保留旧 `search_project` 等外部入口作为兼容 Adapter，不同时维护一份 TS 算法和一份 Rust 算法。最终位置可根据快照读取、权限与现有依赖确认，但统一行为契约不变。

复用当前词法与向量实现、RRF、页面读取和引用解析能力；补齐证据版本、原文位置、多目标状态和开关执行。现有入库专用向量召回及问答的关系摘要逐步迁入，移除重复融合与降级逻辑。词法首期可沿用并改进现有实现；不能将其描述成已实现 BM25，是否更换索引引擎另以效果和性能决定。

避免每次查询重复全库读取正文及重建图；为文件清单、词法、索引导航和引用关系提供按页面版本更新的派生数据，监听应用写入及外部文件变化。派生数据仅用于定位，最终正文仍核实实际版本。建索引不等于允许执行禁用通道；词法或引用解析变更不自动要求重建全部向量，只有向量分块、身份、文本或模型等相关变化才安排相应索引迁移。

### 8.8 参数、评估与待定项

本次已确认的数量如下，按单个问题／检索目标的一轮检索计算，统一配置默认值为 5：

| 参数 | 确认值 | 计数单位 |
|---|---:|---|
| vectorTopK | 5 | 向量通道返回的正文片段 chunk，同一页面可有多个片段 |
| keywordTopK | 5 | 词法排序后的候选页面，再定位其中相关正文 |
| indexPageTopK | 5 | 索引导航选出的目标页面，不是索引页自身的切片数 |
| finalTopK／resultLimit | 5 | 每个目标最终返回的正文证据条数，按 RRF 顺序选择 |

前三个通道各取最多 5 条，合并前最多为 15 个通道候选；重合、过滤和无命中会减少数量，不要求凑满。不同单位先规范到真实页面身份参与融合，再选择正文证据；不能为凑足 5 个不同页面而暗中将向量召回扩大至 30 或 60 个片段。同一页面的多个片段不重复作为该通道的多票。

最终最多 5 条是整个目标的输出上限，不是每个通道各返回 5 条给模型，也不等于读取 5 篇全文。同一页可贡献不同证据；相关上下文在对应证据内展开，受字符预算约束。若多个目标共享同一证据，可以共用正文及 `targetIds`，但每个目标关联的最终证据最多 5 条；不能先汇总所有目标再只保留全任务前 5 条。

图扩展若启用，其候选参与融合并受最终 top 5 限制；实际默认关闭，最多 5 个种子扩展一跳、检查 20 个邻居，不自动给图通道新增最终名额。一次补查仍遵守各通道 top 5 和最终 top 5，补查次数另受上层累计预算限制。数量不足、超时或预算不足时返回真实结果及原因，不静默扩大通道 top-K。

通道默认组合、多目标预算分配、展开字数、图种子／边数、超时与补查轮数在实现时集中配置。不为某一个示例问题硬编码权重或关键词，评估后如需调整已确认的数量，应显式修改配置与方案，不自动恢复此前讨论过的 30＋30→10 建议值。

首期沿用 RRF 常数作为基线；专用 rerank 模型、自动查询改写、默认图扩展以及具体阈值均为可选实现建议，不表示已经确认新增模型依赖。应通过多问题、同语料对照后确定默认参数。

评估同时包含精确标识符、别名、语义改写、多主题、章节后部事实、条件不同的近似观点、真实反例、未入索引页面、过期向量、无答案及引用导航场景。比较单通道与组合通道的相关证据召回、最终排序、版本准确性、上下文完整性、延迟和模型成本；人工标注所需证据，不以回答流畅或生成事项数量代替检索正确性。

## 9. 分类、证据与去重

| 优先级 | 主类 | 子类／界面展示 | 判断约定 |
|---|---|---|---|
| 1 | 合并问题 | 合并问题 | 写入过程中发生判断或合并质量困难，说明实际处理及风险 |
| 2 | 内容冲突 | 内容冲突：本轮页面 | 本轮不同页面对同一对象、版本和条件提出不相容主张 |
| 2 | 内容冲突 | 内容冲突：覆盖前后 | 本轮新页面与该路径入库前快照存在需人工判断的分歧 |
| 2 | 内容冲突 | 内容冲突：已有知识 | 本轮变化与其他当前知识页存在不相容主张 |
| 3 | 内容校验 | 内容校验 | 来源关键内容遗漏、原意改变、归属错误或无依据新增 |
| 4 | 格式校验 | 格式校验 | 字段、结构、类型、目录、链接等不符合规范 |
| 5 | 缺页建议 | 缺页建议：内容成页 | 已有内容分散或嵌在其他页面，值得形成稳定独立入口 |
| 5 | 缺页建议 | 缺页建议：知识补充 | 来源明确提及的重要知识点，检索后未找到对应有效内容或页面 |
| 6 | 疑似重复 | 疑似重复 | 最终仍存在实质重复、分工不清的页面，不仅仅是主题相关 |
| 7 | 研究建议 | 研究建议 | 值得继续验证、比较、补充证据或资料的问题 |

相关约定：

- 已有独立页面但索引漏收，优先作为确定性的索引维护处理，不误报缺页；维护失败说明原因。
- 缺页同时评估重要性、主题独立性和项目页面规则，不要求每个顺带提及术语都建页。
- 来源已明确给出而本次转换丢失的内容归内容校验，不重复包装成知识补充缺页。
- 版本、环境、权限或适用条件不同不直接判冲突；已有双方观点及差异说明时，不反复提出同一待办。
- 合并问题描述处理决策，冲突描述不相容主张；可关联，但不复制相同描述成多条事项。
- 当前页面内部保留的未解释矛盾也应被识别；首次实施可与本轮页面冲突检查共用证据格式，在描述中明确是同页，不新增主类。
- 上述同页情况需在实现时保持名称准确，不能将“本轮页面”误写成一定来自两张文件。

每条新事项至少提供：类型及子类、问题、来源运行、相关页面、可定位证据、实际处理结果、风险点、建议动作。覆盖前后证据通过快照标识读取，不能使用当前页面冒充旧版本。

新事项增加逻辑身份与证据版本。去重不能只靠模型自由生成的标题，也不能仅按 runId 区分所有事项。相同页面和实质相同证据的同一问题复查时更新；证据发生实质变化时记录新发生情况，不能让旧“已处理”状态压掉新问题。

人工已处理、已忽略状态需要绑定其审阅过的证据版本。自动巡检不能只因文件名出现就确认缺页已解决，也不能依赖历史审阅说明再次生成同类事项。历史问题描述不等同于已经验证的知识事实。

## 10. 导入过程与审阅界面

### 10.1 新页签

左侧主导航“资料”之后新增“导入过程”。移除左下角 ActivityPanel 展示，不依赖该面板维持任务执行。原面板中的文件同步、索引等操作迁入新页相应区域或保留在其所属功能入口，其他非导入活动保留所属页面的执行状态。

新页首期采用列表加详情展开，展示当前项目任务和历史：

| 来源 | 当前阶段 | 写入状态 | 审阅状态 | 事项 | 操作 |
|---|---|---|---|---|---|
| 来源 A | 页面合并 | 进行中 | 等待写入 | — | 取消导入 |
| 来源 B | 检索相关知识 | 已写入 6 页 | 审阅中 | — | 查看详情、取消审阅 |
| 来源 C | 等待补写 | 部分写入 3 页 | 已完成部分检查 | 2 项 | 继续补写、查看事项 |
| 来源 D | 已结束 | 已写入 4 页 | 审阅完成 | 3 项待处理 | 查看事项、查看页面 |
| 来源 E | 审阅中断 | 已写入 2 页 | 未完成 | — | 重试审阅、查看原因 |

等待审阅或审阅中时不显示“未发现问题”。只有所有适用检查完成且没有问题，才显示“审阅完成，未发现问题”。已发现问题但检查不完整时同时保留数量和未完成状态。

详情包含阶段进度、时间、实际写入页、处理方式、环境或降级原因、证据入口、审阅范围及历史尝试。只展示真实可计算进度，无法计算时显示阶段名称。

导入和审阅分别提供取消、重试；部分写入使用“继续补写”。批量操作只应用到适用状态，清理历史不等于删除已写 Wiki 文件。

### 10.2 审阅页

- 审阅页集中处理七类事项，按既定优先级排序，同主类保留稳定顺序，子类不另设优先级。
- “导入过程”中的事项数量可跳转，并按来源／runId 筛选。
- 自动审阅完成与人工事项处理完成分别显示。
- 任务失败、排队、取消属于执行状态，不新增一类 confirm 待办来伪装检查结果。
- 卡片直接展示子类、处理结果和风险摘要；正文证据及覆盖对比按需展开。
- 明确动作包括查看证据、发起处理会话、确认已审阅、忽略；不能再将未知按钮文本默认识别为建页。
- 缺页、研究可以提供有材料依据的建页／研究入口。生成知识页必须基于知识材料，不能把审阅说明直接复制成知识页。
- 本次任务产生的其他用户可见问题也进入相同持久化流，不依赖仅在当前项目内存中的 Store。

## 11. 历史数据、提示词与入口兼容

### 11.1 审阅记录

首期保留主类型兼容：contradiction 显示内容冲突，coverage 显示内容校验，structure 显示格式校验，missing-page、duplicate、suggestion 保持可读；新增合并问题及子类型字段。

旧事项缺少子类时显示主类或历史标识，不根据标题猜测补齐。旧 confirm 仅作历史兼容，不继续用于新任务状态。保留旧 ID 映射和已处理／已忽略信息，兼容 API、会话及研究任务对旧事项的引用。

loadReviewItems 从旧 acceptance 报告恢复事项的机制需要保留迁移去重与处理状态，不能每次打开项目都复活已处理事项。旧标题生成的 ID 与新证据身份需要显式兼容，而非全量重新编号。

新流程不再写入旧 acceptance 报告目录；旧报告只作为历史数据读取和迁移来源，不能触发第二套审阅调度，也不能与统一 review 重复发布相同问题。

API／MCP 继续读取现有主类型，新字段向后兼容。会话上下文、研究入口、批量处理和过期事项清理同步适配，不能只改卡片文字。

### 11.2 项目提示词

当前项目会优先读取自定义 Markdown 提示词，不会自动采用新的内置模板。需要版本化新输入契约，提供预览差异、备份和明确迁移结果。

不覆盖用户自定义规则；已知旧占位符需要兼容映射。无法安全迁移时保留旧文件并说明该检查未完成，不能静默传空材料或抛弃用户规则。新 system 放规则、user JSON 放材料的组织方式单独回归验证。

### 11.3 入库入口

自动上传、来源监控、对话材料交接等公共队列入口统一接入。旧对话“保存到 Wiki”入口也需要生成写入记录并交接后台审阅，避免直接覆盖后没有审阅。

纯手工编辑或通用文件写入不因为调用底层 writeFile 就自动启动入库审阅；只有明确的入库／知识保存入口登记任务。无法取得来源原文的保存场景记录内容校验不适用的原因，不能声称已经核对完整来源。

## 12. 分阶段实施

| 阶段 | 工作 | 可验证结果 |
|---|---|---|
| 1 | 固定行为契约、数据类型、写入与审阅状态，建立可靠运行记录和恢复测试 | 旧快照、处理事件、部分写入和审阅交接可追溯 |
| 2 | 改造目标选择与正文合并返回结果，落地降级写入及仅补写 | 内容判断不再触发整次来源反复重导入，并发和实际存储保护仍有效 |
| 3 | 新增独立后台审阅队列，合并 acceptance 与独立 review 为统一任务、协议及持久化流程，分离缓存与重试 | 任务重启恢复、仅审阅重试、无重复发布、失败不回退已写页面 |
| 4 | 建立统一证据检索核心及输入输出协议，接入入库与 review，并迁移问答／搜索的检索 Adapter；完善七类结果协议 | 各入口遵守同一开关、融合、引用关系及版本契约，三种冲突、两种缺页等有可定位正文证据 |
| 5 | 导入过程新页、移除左下面板、卡片分类排序和明确动作 | 用户可查看任务历史、补写、单独重试及按来源处理事项 |
| 6 | 数据和自定义提示词迁移、旧入口与 API／MCP 兼容、真实模型评估 | 旧人工状态不丢失，各入口行为一致，误报与成本有记录 |

各阶段保持可运行，但在后台交接、快照及版本保护具备前，不启用会改变旧页的降级覆盖策略。

## 13. 验证与验收

不使用全量构建或格式检查替代行为验证。优先运行受影响的 Vitest 单测与真实文件集成测试，随后检查类型与必要构建；真实模型效果单独记录。

| 场景 | 必须验证的契约 |
|---|---|
| 内容歧义、合并正文过短、返回无效结构 | 新稿按约定写入，旧快照可读，处理结果和风险可追溯 |
| 多个目标、主题不确定 | 原候选不被任意覆盖，新页落盘，产生合并问题 |
| 覆盖前后、本轮多页、跨来源知识冲突 | 分类准确，双方证据可定位；版本和条件差异不误报 |
| 同页与多页的未解释分歧 | 保存完整证据，不因同路径而跳过，也不重复报告相同页面对 |
| 内容已存在但无独立页面／来源知识尚未收录 | 区分内容成页与知识补充，已写入丢失归内容校验 |
| 向量库可用、未启用、失败、过期索引 | 正确选择检索方式；读取最新正文，不把失败当不存在 |
| 通道开关、项目覆盖、全部关闭及失败降级 | 明确禁用通道不被调用，所有入口使用相同有效配置，未执行检索不被解释为没有相关知识 |
| 同一查询从入库、review、问答和搜索进入 | 在相同范围、配置和预算下检索契约一致；各阶段业务决策不混入检索核心 |
| RRF、多次改写、单通道命中 | 融合不相加异构原始分数，不因重复改写刷高排名，结果条数与平滑参数分开 |
| 三通道 top 5、多目标 final top 5 | 每个通道每个目标最多 5 条，最终每目标最多 5 条；无命中不凑数，改写、图扩展和正文展开不绕过限额，多个目标不被全局前 5 条截掉 |
| 同页多片段、重叠片段、多目标请求 | 重叠命中合并、独立事实保留，每个目标都有证据及状态，不因总排序造成主题遗漏 |
| 图扩展、出链、反向链接、锚点及重名目标 | 原始方向和定位可追溯，歧义不任意解析，无关导航邻居不挤占结果，正文及关系实际进入模型材料 |
| 有链接但未读正文、旧片段无法重新定位 | 不把关系当成目标正文，不将旧事实换上当前版本指纹；缺口明确记录 |
| 多轮补查、超时、部分通道失败 | 共享累计预算且有限结束，保留有效证据，区分失败、部分完成和正常无命中 |
| 名称不同、内容嵌在章节、索引漏收 | 能扩大查询核实，避免只按同名判缺页或重复 |
| 本轮页面未入向量库 | 仍可互查并发现相关已提交内容 |
| 来源很长、候选正文超预算 | 分段／展开检查，未检查部分不冒充已通过 |
| 生成截断、补写、完全无可写页 | 完整块保留，状态真实，只补未完成，不写完整成功缓存 |
| 写后崩溃、审阅未排队、审阅中重启 | 恢复交接与任务，不重复生成或覆盖已写页面 |
| 审阅失败或取消 | 已写页不变，可单独重跑，保留已得到的有效问题 |
| 原 acceptance 与独立 review 合并 | 一次后台任务、一份报告、一处发布事项，失败步骤可单独恢复，旧报告不触发重复检查与发布 |
| 并发写入、人工编辑、项目切换 | 不覆盖新版本、不串项目、不发布假定为当前的过期证据 |
| 重跑、忽略、修复后再出现 | 事项按证据版本更新，旧人工处理状态不误压新问题 |
| 旧记录、旧 ID、自定义模板、API 引用 | 兼容加载、处理状态保留，无法迁移有明确说明 |
| 界面导航、排序与动作 | 七类顺序准确，子类可见，切页不停止任务，“已审阅”不建页 |
| 审阅说明曾被保存成知识页 | 不仅凭旧问题标题重新提出当前确定性结论，需读取实际证据 |

真实模型评估使用多种自定义事实的正反样例，包括不冲突的版本差异、实际冲突、无需独立成页、需要整理成页、研究问题等；避免只靠模型熟悉的公共常识样例得出有效结论。

记录准确性、误报、遗漏、待人工判断比例、检索命中和降级情况、请求次数及耗时。不能用事项生成数量作为改造成功标准。
