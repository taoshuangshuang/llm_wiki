# LLM Wiki MCP 与 HTTP 调用对照

测试日期：2026-10-30。应用版本：0.6.12。项目：元数据-LLM-WIKI。基准问题原文：`imeta 是什么`。

## 结论

MCP 最终通过 HTTP 调用同一个后端。单次基准没有发现 MCP 的回答质量优势；两条通道的纯搜索页面、顺序、分数一致。HTTP 更便于控制参数和保存结构化响应，适合作为当前本地 skill 的默认通道。

已实测确认的优化是：原始响应保存为文件，向当前助手只输出最终回答、精简引用和统计。它不会改变后端答案，但能避免大量过程记录淹没回答。HTTP standard 本次从 889839 字节缩减至 3878 字节，减少约 99.56%。这只减少工具上下文，不等于降低后端模型的输入或推理成本。

## 测试条件与限制

基准 MCP/HTTP 均使用 standard、topK=5、includeContent=false、wiki=true、web=false、anytxt=false；固定相同项目、无历史会话、不持久化会话。事件中使用的模型均为 custom:GLM-5.3-Flash。

每个配置仅运行一次，部分请求并发，存在模型非确定性、服务负载和缓存影响，耗时不用于推断通道固有性能。没有重跑桌面 UI，只与用户截图作来源覆盖的定性比较。概念优先组同时修改提示与 topK，因此不能独立归因某个参数，也不能将单个问题的结果推广为所有问题的最佳配置。

## 结果

| 配置 | 耗时 | 引用数 | 模型调用数 | 返回大小 | 观察 |
|---|---:|---:|---:|---:|---|
| HTTP standard，原问题，topK=5 | 124.82秒 | 8 | 4 | 889839字节 | 查询与历史结构为主，未调用 read_page |
| MCP standard，原问题，topK=5 | 177.82秒 | 12 | 7 | 172245字节文本 | 同样偏查询与历史结构，未调用 read_page |
| HTTP fast，原问题，topK=5 | 417.75秒 | 17 | 12 | 2489141字节 | 9次搜索、2次列目录；本次并未提速 |
| HTTP standard，概念优先提示，topK=10 | 437.12秒 | 13 | 15 | 2245961字节 | 3次搜索、8次列目录、3次read_page；读到主题页但有重复 |
| HTTP search，query=imeta，topK=10 | 0.817秒 | 4个结果 | 不触发问答生成 | 180664字节 | 搜索仍带大量证据结构 |
| MCP search，query=imeta，topK=10 | 2.441秒 | 4个结果 | 不触发问答生成 | 已保存格式化结果 | 页面、顺序、分数与HTTP相同 |

搜索耗时不包括后续读取和最终作答，不能与完整 chat 耗时当作同一任务比较。topK 是请求参数，本次不保证实际返回10条，也不是最终多轮累计引用数的上限。

HTTP standard 的8条引用均包含在MCP的12条引用中。两次基准都引用了回答未读取的关联页面路径，不能把回答内出现路径等同于已验证全文。

## 返回体为什么大

HTTP standard 的 references 含 knowledgeContext；events 含工具过程输出；toolEvents.detail 又包含序列化检索证据。

MCP 虽不输出原始 events，但 formatChatResponse 会把 toolEvents.detail 原样拼到文本，仍然产生约172KB输出。去掉其 Tool events 后剩8179字节。

对应实现：mcp-server/src/api-client.ts 的 chat 调用 HTTP /chat；mcp-server/src/index.ts 的 formatChatResponse 格式化回答；src-tauri/src/api_server.rs 的 external_chat_response 返回完整事件字段。当前请求结构没有事件输出级别开关，includeContent=false 也不保证响应精简。

## 推荐优化顺序

1. 保持 HTTP 通道，默认 standard；保留用户原问题，不擅自添加MDD、YPD等方向。原始JSON落盘，返回原始答案和精简引用，不请求模型重新生成或重发答案。
2. 原问题对照测试统一项目、模式、检索模式、模型、skills、contextFiles、历史。UI可以传入模型配置与显式历史；当前MCP schema未暴露retrievalMode/contextFiles/history等全部字段，因此通道一致不代表调用配置自动一致。
3. 如果要求应用自身回答，继续调用 /chat；如果接受由当前助手回答，可采用 search → read关键页面 → 当前助手综合。纯搜索已有实测，但这个受控流程的完整质量与耗时尚未做端到端验证。
4. 对“是什么”类问题，优先验证概念/主题/总览来源，再补充约束和案例；检索无定义时扩展相关术语，而不是反复使用同一个宽泛词。作为后续通用策略，不硬编码imeta页面路径。
5. Agent内部可进一步限制无新增证据的搜索/目录循环，避免重复读同一页面，并设置明确时间/轮次预算。本次没有修改这些生产行为。
6. 如优化服务端体积，可增加兼容的返回级别参数，例如answer/references/debug；普通模式不附完整knowledgeContext及工具输出。MCP对应只输出工具概要。该项为设计建议，尚未实现。

## 概念优先组的完整提示
