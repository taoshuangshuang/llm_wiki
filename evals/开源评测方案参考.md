# 开源 skill 评测方案参考

> 当前实现已收敛为回归验证：无基线对照和历史产物，仅保留每个 case 最新输出、一份 HTML 汇总及版本结果摘要。下文列出的是上游能力与早期设计参考；实际使用以 `用例格式说明.md` 和已安装 `skill-validator/SKILL.md` 为准。

核对日期：2026-10-16。以下将官方能力与本项目建议分开；链接指向上游当前文件，实际采用时应固定提交版本。本文仅为调研，没有安装工具、执行模型或验证这些框架在本项目的兼容性。

## 三个项目分别借鉴什么

| 项目 | 官方已有设计 | 对本项目的启发 |
| --- | --- | --- |
| Anthropic skill-creator | 测试定义包含请求、输入文件和预期说明；运行结果按迭代、用例、版本组织。新 skill 对照无 skill，修改现有 skill 对照旧版快照。汇总通过率、耗时、token 的均值、标准差和差值；HTML 展示产物、评分和前次反馈，并导出 `feedback.json`。触发描述另有正反例测试及训练／留出划分。[工作流源码](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md#running-and-evaluating-test-cases) | 保留可追溯的每轮目录；反馈落文件，能够用于下一轮，而非只保留一张报告截图。 |
| Promptfoo | YAML 驱动版本对照；同任务、文件、模型和权限，只替换 skill。支持输出断言、触发断言、耗时和成本检查；可重复运行、禁用缓存、输出 JSON，并使用网页并排查看。Codex 的 `skill-used` 依据成功读取对应 `SKILL.md` 推断。[官方指南](https://www.promptfoo.dev/docs/guides/test-agent-skills/) | 作为后续批量执行与展示工具；读过 skill 与产物正确分别验收。 |
| SkillsBench | 当前任务包由 `task.md`、`environment/`、`oracle/solve.sh` 和 `verifier/` 组成；任务描述含超时与资源配置。冻结输入、固定依赖；验证器检查产物，参考解应先取得满分；比较有无 skill，skill 运行时注入，避免无 skill 组仍读到同一份 skill。[贡献规范](https://github.com/benchflow-ai/skillsbench/blob/main/CONTRIBUTING.md#task-package) | 借鉴任务包和验证器边界；复杂任务再采用容器隔离，不必第一版完整搬入其执行系统。 |

skill-creator 的评分器要求查看记录与真实文件，逐项保存 `text`、`passed`、`evidence`，也检查验收规则是否太弱，例如仅检查文件存在却不检查内容。[评分器源码](https://github.com/anthropics/skills/blob/main/skills/skill-creator/agents/grader.md)

SkillsBench 的审查规则明确拦截把测试／参考解复制进 Docker 镜像的情况，并审查执行轨迹中的作弊及“读过 skill 但没完成流程”。因此，答案目录与执行环境分离有明确来源；**仅在同一可读目录中分文件夹，不等于实现隔离**。[任务审查规则](https://github.com/benchflow-ai/skillsbench/blob/main/.agents/skills/task-review/SKILL.md#step-3--static-policy-check)

SkillsBench README 当前默认云端执行使用 Modal，也提供 Docker 本地运行；与内部审查 skill 中部分后端说明不同。本项目只借鉴隔离原则，具体接入时以锁定版本的 CLI 帮助和实际运行结果为准。[README](https://github.com/benchflow-ai/skillsbench#quick-start)

## 本项目建议：一个用例应能回答七个问题

以下是设计建议，并非三个框架共有的强制格式。

1. **测什么**：用例 ID、来源问题、场景、用户原始请求；触发测试和效果测试明确分开。
2. **给什么**：冻结的原始文件、schema、purpose、已有页面，以及输入内容指纹。
3. **在哪里执行**：依赖、工具权限、网络、超时、预算、初始目录；每次从干净副本开始，正式知识库不作为输出目录。
4. **怎么执行**：准备、执行、检查三阶段；命令、工作目录、参数和必要环境变量名称写明。密钥从运行环境取得，日志脱敏。
5. **什么算正确**：必要结果、禁止结果、可接受变化、判定方式、规则版本。输出缺失必须失败；模型标题和措辞不宜逐字比对。
6. **实际发生什么**：原始产物、请求／响应或执行轨迹、错误、耗时、可获得的用量；不能只保存最终回答。
7. **比较后怎么办**：相对基线的改善、退步、无变化与待复核项；人工反馈、采纳决策及下一轮待办落文件。

## 输出报告建议

同一运行同时生成机器可读 JSON 和可浏览 HTML，二者使用同一评分数据。每个用例至少展示：

- 请求与输入链接、基线／候选版本、每次重复的结果。
- 每条验收规则的状态、实际值、失败理由、证据文件与定位。
- 两版产物与差异；复杂产物保留可打开的原文件。
- 耗时和用量；获取不到的值记为未知，不能当作零。
- 人工意见以及是否接受本次修改。

总览同时区分“用例通过率”和“验收项通过率”，列出分子分母。重要规则失败单独显示，避免被平均分掩盖；执行失败、评测环境故障和待人工判定分别呈现。

## 容易遗漏的约束

- **公平比较**：固定输入、模型、参数、工具与依赖；保存代码、提示词、整个 skill 资源包和评分器版本。一次比较尽量只改变一个因素。历史基线遇到模型服务变化时需标明局限，必要时同批重跑。
- **防结果污染**：旧输出、缓存、断点和会话上下文均需纳入重置范围。回放响应适合程序回归，但不能作为新提示词有效的证据。
- **防答案泄漏**：执行者只获得输入和公开任务要求；内部验收材料、参考答案、基线产物和历史反馈由执行器在代理不可访问的位置保存。知识类任务允许给公开规范，但不能把本题最终答案伪装成规范输入。
- **验证检查器**：准备正确、错误、空文件等样本，确认检查器能识别。主观评分需固定量规、裁判配置与原始判词，并保留人工复核。
- **处理波动**：先单次跑通，再对重要或接近的结果重复；同时呈现每次结果与汇总，不能挑最好一次。
- **避免过拟合**：真实失败变成回归用例；还要保留成功、相邻类型、反例及未用于调优的用例。新增验收规则后应重评旧版产物，规则改变前后的总分不可直接比较。
- **报告后要有决策**：通过已知样例只能支持当前范围的判断，不能保证持续提升；反馈应改进通用规则，不能把样例答案塞进 skill。

第一版可先做固定输入、干净临时目录、确定性验收、版本快照和 JSON／HTML 报告；触发评测、容器、模型裁判与 CI 按需要逐步加入。
